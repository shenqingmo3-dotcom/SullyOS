## 1. 项目最终目标

在 SullyOS 前端之外建立一个常驻后端，让角色不依赖网页一直打开也能保持统一的角色设定、聊天和记忆，并能按心跳自主决定：

- 什么都不做；
- 主动发消息或碎碎念；
- 每天最多写一篇独立日记；
- 预约下一次准确唤醒；
- 浏览小红书、X、网页或调用多个 MCP；
- 请求查看用户的 iPhone 屏幕并作出符合人设的反应；
- 把日记、工具活动、分享内容和记忆变化以正确类型同步回前端。

核心体验不是“定时群发”，而是角色像一个有自己时间的人。所有自主结果都必须先经过角色人设、关系、记忆和当前情境消化，再以角色本人会使用的口吻表达。

## 2. 已确定、不能随意推翻的产品决策

### 数据与模型

- PostgreSQL 是后端权威数据源；前端 IndexedDB 是离线缓存和交互副本。
- 前后端有关的数据必须双向一致，尤其是聊天、记忆、日记、评论和删除操作。不能出现“前端删了，后端刷新后又复活”。
- 手机的备份比电脑新。正式启用 VPS 心跳前，必须先把手机最新完整备份导入选定前端，再执行一次完整同步与 reconcile。
- 同一份备份重复同步应按稳定 ID 去重；不要把电脑和手机两个不同快照分别当权威源直接灌入后端。
- 普通聊天默认继续走 SullyOS 前端现有模型池，不要擅自改用户从 API 站购买的 URL、Key 或模型配置。
- 后端模型池主要服务心跳、自主活动、后端日记等常驻任务；前端“使用新后端聊天”只能是可选路径。
- 提示词只能组装一次。不能把完整前端系统提示词和完整后端原生上下文叠两遍。

### 自主活动

- 每个角色必须有独立开关；先只开最常聊天的角色。
- 心跳先做低成本门控：启用状态、空闲阈值、活动时段、冷却、概率，再调用模型。
- 心跳检查间隔、空闲阈值、活动时段、冷却和概率档位需要热更新。
- 预约唤醒与概率心跳并存；预约到点时不再经过随机概率和普通冷却。
- 日记每天最多一篇。零散想法应直接发到聊天，不要强行写成日记。
- 日记是用户与角色各自独立写作；互动通过便签/评论完成，不是“用户写一篇，角色被迫回写一篇”。
- 工具一旦由角色主动决定调用并成功得到结果，后置阶段不应再次抽签沉默；结果要由角色评价、吐槽、关心、追问或分享。
- 小红书和 X 的浏览、点赞、评价、转发、分享属于各自平台能力，不要再造一个重复的“对外写入”总开关。
- MCP 不能只有一个“主 MCP”，需要支持多个连接，由角色在可用工具里选择。

### 前端表现

- 普通回复、主动消息、AI 日记、自主活动、MCP 记录、记忆变化、预约事件应保留事件类型，不能全部塞成普通气泡。
- X 分享应和小红书 Lite 分享一样显示内容卡片，而不只是裸链接。
- 前端普通聊天调用 MCP 后也应有可视化卡片。
- 手机查岗不需要额外“活动卡片”：角色请求截图 → 用户手机回传截图 → 截图出现在聊天 → 角色直接反应并推送。
- UI 不要重复已有模块。小红书 Lite、通用 MCP、推送等已有入口应合并复用。
- 代码和界面都要短、直观、响应快；不要为了极少数情况堆叠备用链路、冗长判断和重复状态。

## 9. 整段对话中可以避免的坑

1. **不能把计划说成已经部署。** 之前用户最不满意的一点，是没有拿到 VPS 登录信息、没有实际检查服务器，却给出像“已经部署”的措辞。以后必须用命令、容器状态和 healthcheck 证明。
2. **不要不断改变架构口径。** 普通聊天是否走后端、前端提示词是否保留、ASMG2 是否继续使用，曾多次表述不一致。当前口径已经固定：普通聊天默认前端模型池，后端负责常驻自主能力和统一数据；后端聊天是可选。
3. **不要创造重复入口和重复权限。** 小红书 Lite、MCP、X、Web Push 已有对应位置，应在原位置扩展。不要再造“外部写入”“主 MCP”“Instant Push”重复设置。
4. **不要把工具结果直接当角色输出。** 抓取/截图结果先是客观材料，真正发给用户的必须是角色消化后的表达。
5. **不要在调用成功后再次随机沉默。** “要不要看”发生在工具调用前；角色既然主动看了，成功结果就应形成反应。
6. **不要误解日记互动。** 用户日记和角色日记是两条独立记录；评论便签才是互动。
7. **不要只做前端删除。** 所有触及后端的数据删除都必须同步 tombstone/删除接口，否则刷新后会复活。
8. **不要用调大限制掩盖错误。** 十万关系 ID 的报错应通过分片和快照 reconcile 解决，而不是无限提高单请求阈值。
9. **不要同时把两台设备当权威源。** 先选手机最新备份，导入后再统一同步。
10. **不要让日程出现双重真相。** 复用现有日程存储，在同步边界产生后端快照；避免 character 字段和独立 store 长期双写。
11. **不要破坏每日零点刷新。** 用户明确要求保留 SullyOS 本体的自动日程生成。
12. **不要在功能未收束时频繁部署。** 先完成一组功能、自动检查、本地验收，再打一次可追踪的部署包。
13. **不要为了“保险”堆大量 fallback。** 用户明确要求少考虑极罕见情况，避免后端计算冗长和前端响应慢。
14. **不要泄露或索要账号密码。** 登录状态使用 Cookie 注入、设备令牌或用户自己操作的远程桌面；服务器用 SSH key。
15. **不要覆盖原版升级路径。** 后续同步 SullyOS 上游功能（如 PWA 图标）时，应先提交/保存当前二改，再小范围合并上游，不要在巨大脏工作区直接全量覆盖。
